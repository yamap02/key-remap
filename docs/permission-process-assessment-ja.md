# ReKey の権限・プロセス削減の実現性

調査日: 2026-10-25（JST）／対象コミット: `0886897`／実機: macOS 27.0.1、インストール済み ReKey build 3。

追記: 第一候補を実装した結果は [入力サービス統合・権限整理の実装と検証](consolidated-service-validation-ja.md) を参照。以下は実装前の評価として保存する。

## 結論

**削減できる。ただし、「許可項目」「強い権限を持つコードの範囲」「常駐プロセス数」は別々に最適化する必要がある。**

最初の実装候補は、`rekey-core` と `rekey-vhid` を統合して **ReKey 固有の常駐を4→3、root プロセスを2→1** にする構成。ユーザーセッション側の Agent は残す。アクセシビリティは通常のリマップの必須条件から外し、EventViewer 利用時だけ要求・使用する。

全機能を使う場合、現方式では入力監視・アクセシビリティ・ドライバ拡張承認・バックグラウンド実行承認は引き続き必要。4種類を1種類へまとめる案は、同じ機能・安全性を保つ方法としては根拠がない。画面上の4カードは、同じ入力を見る4つの重複権限ではない。

これは実装前の評価であり、統合後の機能同等性を実機で証明したものではない。アプリ、権限、サービス登録は変更していない。

| ReKey Agent | user / 88431 | 最前面アプリ・入力ソース、プロファイル自動切替、ホットキー、ユーザーアクション、AX フォーカス判定 | ユーザーセッションで動かす意味がある |
| rekey-core | root / 86168 | 物理 HID 占有、ルール変換、デバイス別処理、緊急停止、イベント秘匿 | 入力監視の実際の利用先 |
| rekey-vhid | root / 86167 | 変換済み出力を Karabiner の接続デーモンへ転送 | Core との統合候補 |

インストール済み UI・Agent・Core・VHID の4実行ファイルは、ローカル `build/ReKey.app` 内の対応ファイルと SHA-256 が一致。インストール済み app の `codesign --verify --deep --strict` も成功。ただし今回リビルドしておらず、現在のソースからの再現ビルドまで確認したわけではない。

システム設定では次を確認した。

- 入力監視: `rekey-core` がオン。さらに `ReKey-before-setup-fix.app` もオンで残存していた。
- Device Control and Data Access（アプリ内表記はアクセシビリティ）: `ReKeyAgent.app` がオン。
- バックグラウンド実行: `ReKey.app` がオン。ドライバ拡張の一覧にも Karabiner が存在し、対応ドライバの実プロセスを確認した。

`ReKey-before-setup-fix.app` は旧版と見られるため、**追加調査後に解除する候補**。表示名だけでは登録先・コード署名の同一性を確定できないので、現行 Core の許可まで失わないことを確認して整理する。今回この許可は操作していない。

## 権限ごとに減らせる範囲

| 権限・承認 | 用途 | 全機能を維持した削減可否 |
| --- | --- | --- |
| 入力監視 | Core が物理キーボードを取得 | Core 1個への許可を維持。UI・Agent への重複許可は不要 |
| アクセシビリティ | EventViewer のパスワード欄・不明フォーカス判定 | 普段は未許可でリマップ可能にし、EventViewer 利用時に要求できる。EventViewer の秘匿動作を維持した完全廃止は未解決 |
| システム／ドライバ拡張 | 仮想 HID 出力 | 現方式では維持。単なるプロセス統合では消えない |
| バックグラウンド実行・特権サービス登録 | ログイン後の常駐、root 出力経路 | 維持。ReKey 独自の root サービス登録は2個から1個へ減らせる候補 |
| 通知 | `notify` アクション | そのアクション使用時だけ要求する現在の方針を維持 |

根拠は `Sources/ReKeyAgent/main.swift` の `tick()` / `execute()`、`Core/core.mm` の `tick()` / `record()` / `events()`。入力監視は Core 自身で確認・要求し、Agent は `AXIsProcessTrusted()` とフォーカスの role / subrole を参照している。AX で入力文字列を取得する実装ではない。

最前面アプリ取得、入力ソース取得、プロファイル切替、Carbon ホットキー、ユーザー権限でのコマンド実行には、このコード上 AX の許可条件はない。Core も AX 未許可を理由に通常のリマップを停止せず、EventViewer の表示を止める。このため、通常機能と EventViewer の権限要件を UI でも分けられる。

ただし「必要時だけ使用」は「OS の許可が自動で期限切れになる」という意味ではない。一度付与した AX 許可は OS に残る。より強く利用期間を限定するなら、AX フォーカス監視を専用ヘルパーへ切り出し、EventViewer 使用中だけ起動する。これは常時権限を持つコードを減らせる一方、表示中のプロセスが1個増えるため、プロセス最小化とは別案になる。

`IsSecureEventInputEnabled()` だけに置き換える案は勧めない。現在はそれに加えてパスワード欄・AX 取得失敗・Agent からの状態が500 ms以上古い場合も表示を抑止している。AX を削除するだけでは、この追加の保護まで同等に維持できない。なお現在の100 ms周期のフォーカス判定自体についても、切替直後の競合を含む完全な秘匿保証を今回証明してはいない。

Apple の [AXIsProcessTrusted](https://developer.apple.com/documentation/applicationservices/1460720-axisprocesstrusted) は現在のプロセスの AX 信頼状態を確認する API。統合後も許可が「コード中のフォーカス判定関数だけ」に限定されるわけではない。

## プロセス削減案の比較

個数は ReKey 固有のみ。Karabiner の2プロセスと OS の UI サービスは別計上。

| 案 | 常駐数 | root 数 | 機能・権限への影響 | 判定 |
| --- | --- | --- | --- | --- |
| 現状 | 4 | 2 | UI と Agent、Core と VHID がそれぞれ別 | 比較基準 |
| A: Core と VHID を統合 | 3 | 1 | ユーザー側の役割・許可先を維持しやすい。障害回復は再検証必要 | 第一候補 |
| B: A に加えて UI と Agent を統合 | 2 | 1 | AX を設定 UI と同じプロセスに付与。UI 終了後の動作も再設計が必要 | 最小権限を優先するなら保留 |
| C: ユーザー側を統合し、AX だけ必要時ヘルパー | 通常2、EventViewer 中3 | 1 | UI・コマンド実行から AX を分離できる。終了・再起動・状態引継ぎの設計が大きい | 中長期候補、同等性未検証 |
| 全部を1つの root アプリへ統合 | 1 | 1 | UI、JSON 編集・インポート、shell 実行まで root の範囲に入る | 不採用 |

### A: Core / VHID 統合の具体的な成立条件

現状は Core → root 専用共有メモリ＋UNIX ソケット → VHID → 公式 Karabiner Daemon → DriverKit という経路。Core と VHID はいずれも root であり、Core が送る変換済み入力を VHID が HID レポートへ変換している。

VHID のレポート組立と `service::client` を Core 内の出力クラスへ移せば、共有メモリ・通知ソケット・VHID 独自 launchd 登録をなくせる。新たな権限種類を増やさずに実現できる設計上の見込みがある。ただし root プロセス数が減っても、入力を処理する Core 自体の root 権限は残る。

分離には障害時の利点もある。現 VHID は Core の切断を検知して全キーを解放する。統合後は Core のクラッシュと出力処理のクラッシュが同時になるため、別プロセスの同じリセット処理には頼れない。Vendor のサーバーにはクライアント切断時にクライアントを破棄する実装があるが、これだけでキー残留や復帰時間が同等と断定しない。

統合時は次が必須になる。

- 出力クライアントを入力処理とは別のキュー等で動かし、HID 送信待ちで物理入力を塞がない。
- 複数デバイスの同一キー押下カウント、修飾キー、consumer / Apple vendor 系レポートを維持する。
- ドライバ ready を確認してから占有し、出力切断・キュー超過・緊急停止時に全キー解放と占有解除を行う。
- Core 強制終了・ハング、デーモン終了、ドライバ再接続、スリープ復帰でキー残留と物理入力回復を確認する。
- 旧 VHID サービスを解除してから新 Core を起動する移行を作る。二重送出や古い共有メモリへの接続を防ぐ。

### B / C: UI と Agent の統合が単純ではない理由

Agent は GUI を持たないユーザーセッション常駐で、現在は UI を終了しても別プロセスとして残る。`disable_on_quit=false` の場合に継続するアプリ条件・入力ソース条件・ユーザーアクション・ホットキーを、統合アプリの終了と一緒に失ってはいけない。ウィンドウを閉じた状態と、明示的にアプリを終了した状態も区別する必要がある。

さらに現 Agent は AX 判定と `shell_command` 実行を兼務する。root ではないが、すでに同じ AX 許可主体に2つの責務がある。最小権限をさらに進めるなら、この分離も検討対象となる。単に UI へ移すと AX を持つコード範囲がさらに広がる。

公式 Karabiner も、AX フォーカス監視とユーザーコマンド実行を別プロセスに分ける理由を[セキュリティ文書](https://karabiner-elements.pqrs.org/docs/help/advanced-topics/security/)で説明している。ReKey に同じ個数を強制する理由にはならないが、プロセス分離の意味を判断する材料になる。

## root とドライバをさらに減らせるか

**現在の公式 Karabiner 出力経路を使う限り、出力クライアントの root は外せない。** Vendor README と現行の[公式 README](https://github.com/pqrs-org/Karabiner-DriverKit-VirtualHIDDevice#readme)には、クライアントを root で動かす条件がある。実装も root 専用ディレクトリへ IPC ソケットを置く。権限を緩めてユーザープロセスに接続させる変更は採らない。

Core の「入力取得部分だけ」をユーザー権限へ落とす可能性は別途検証できる。現在の `geteuid()!=0` チェック、root 専用 IPC、共有メモリの所有者条件は製品側の制約も含むため、コード中の root チェックだけを根拠に「macOS が入力取得全体に root を必須とする」とは断定できない。ただしチェックを消すだけでは動かず、USB / Bluetooth / 内蔵の占有、セッション切替、IPC 認証、同一ユーザーの他プロセスからの保護まで PoC が必要。今回未実施。

公式接続デーモンを消してドライバへ直接接続するには、DriverKit user-client の entitlement や署名・許可条件の対応が必要となる。独自ドライバへの変更も配布・互換性・承認の仕事を伴い、今回の小規模整理の範囲を超える。Apple の申請・プロビジョニングが必要な条件は公式 README に明記されている。

Event Tap と `CGEventPost` へ全面置換するとプロセス・ドライバを減らせる可能性はあるが、デバイス単位の物理占有、内蔵キーボード無効化、Secure Event Input 中の挙動などに差が出る。現在の全機能を保つ代替としては採用できない。公式の[開発文書](https://github.com/pqrs-org/Karabiner-Elements/blob/main/DEVELOPMENT.md)にも Event Tap のデバイス識別とセキュア入力に関する制約が記載されている。

ThemeWidgetControlViewService は実行パスから Apple の AppKit サービスと確認した。どの UI 部品が起動原因かは未特定。停止しても UI 利用で再生成され得るため、任意に停止する削減策とはしない。

## 追加の改善点と推奨順序

1. **旧許可の整理と権限表示の分離。** `ReKey-before-setup-fix.app` の実体を特定して不要なら解除。通常リマップに必要な承認と、EventViewer・通知など機能使用時の承認を UI で区別する。
2. **Core / VHID を統合して固有4→3を目指す。** 先に障害時のキー解放・回復の合格基準を定め、それを満たしてから旧サービスを廃止する。
3. **定期処理を減らす。** Core は5 ms周期（200回/秒）、Agent は100 ms周期（10回/秒）。Agent はそのたび AX 判定と XPC 操作を行う。UI の状態更新は3秒周期。プロセスの個数だけでなく、入力待ちの起床回数・仕事量を下げる価値がある。長押し等の締切処理と AX 状態の鮮度を維持し、イベント通知と必要なタイマーへ置き換える。CPU 削減量は未計測。
4. **さらに必要なら AX 専用ヘルパーとユーザー常駐の再構成。** 通常2・EventViewer 中3の案 C を検証する。UI 終了時の既存動作を守れる設計と移行を先に確定する。

XPC の権限範囲にも改善余地がある。現 Core は UI と Agent の署名条件を OR で許可し、接続後は同じインターフェースを公開する。現ユーザー照合はあるが、UI / Agent 別のメソッド制限はない。統合に合わせてフォーカス報告・アクション取得・イベント取得などの呼び出し元を制限すると、権限の用途を狭くできる。これは独立した変更として検証する。

## 実装後に必要な同等性確認

単純・複合・同時押し・長押し・レイヤー、デバイス別設定、複数キーボードの修飾キー、アプリ／入力ソース条件、自動プロファイル、ホットキー、shell / open_app / 入力ソース変更 / 通知を確認する。

特に、AX 未許可でも通常リマップが動くこと、EventViewer の通常表示とパスワード欄・Secure Event Input・状態途絶時の非表示、緊急停止、ログアウト／ユーザー切替、UI 終了時の `disable_on_quit` 両設定、再起動・スリープ・障害復帰を実機で確認する。メニューバー表示と設定保存も維持する。

今回行ったのは読み取り調査、インストール済み実行ファイルの照合、署名確認、文書作成のみ。新構成のビルド・入力試験・性能測定は行っていない。実装を変更していないため、既存テストの再実行によって統合後の動作を検証したとの扱いもしない。

## 主なローカル根拠

- `Core/core.mm`: 入力占有、5 ms tick、セキュア入力時の表示抑止、UI 生存期限、XPC 接続認証。
- `Core/vhid.cpp` / `Core/Transport.hpp`: root 専用通信、レポート生成、Core 切断時のキー解放。
- `Sources/ReKeyAgent/main.swift`: 100 ms tick、AX 判定、自動プロファイル、ホットキー、ユーザーアクション。
- `Sources/ReKeyIPC/FocusPrivacy.swift` / `Sources/ReKeyApp/RuntimeClient.swift`: フォーカス秘匿条件、EventViewer の許可条件。
- `Sources/ReKeyApp/ReKeyApp.swift` / `AppState.swift` / `Resources/jp.example.rekey.*.plist`: UI 終了、サービス登録、常駐設定。
- `Vendor/VirtualHID/README.md` / `src/Daemon/include/virtual_hid_device_service_server.hpp`: 出力クライアントの root 要件、root 専用ソケット、接続切断処理。
