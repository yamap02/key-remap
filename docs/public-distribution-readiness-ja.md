# インターネット公開・配布の準備

最終更新: 2026-11-14

この文書は、ソース公開と実行可能な製品の配布について、担当者が判断・運用するためのチェックリストです。文書の作成は各確認の完了を意味しません。項目ごとに対象コミット、成果物、日時、担当者、証拠と結果を残し、未実施・失敗・判定不能を区別します。公開後もリリースごとに確認します。

## 現在の前提と公開判断

- Apple Developer Program には今回登録していません。Developer ID の取得、製品版の署名・公証と、実際の証明書による配布検証は保留です。開発用 ad-hoc 署名や未公証 pkg を公開版の代わりにしません。登録後の手順は [Sparkle 配布手順](sparkle-distribution-ja.md) にあります。
- ソース公開と実行可能な製品の出荷は別に判断します。ソース公開にも履歴、秘密情報、権利の確認が必要です。実行可能な製品は、署名・公証に加えて以下の検証と既存の[要件表](requirements.md)を満たすまで一般配布しません。
- 現在の対応対象は macOS 27 と Apple Silicon です。実際に試験した OS・機種・ドライバを公開時に示し、未試験の組合せを動作保証しません。公式ドライバの利用と独自 DriverKit 拡張の要否は別途判断します。

## 配布元と更新の運用

- [ ] 配布者と公式サイト、ソース、Releases、更新 feed の正規 URL を決め、相互にリンクする。利用者には正規の取得先、版、対応環境、発行者、ファイルの SHA-256 と検証方法を案内する。ハッシュは署名・公証の代わりにはならない。
- [ ] GitHub・DNS・配信先・CI の管理者を必要最小限にし、多要素認証、復旧手段、アクセス棚卸し、変更履歴を整える。タグと公開済み asset の変更・削除の権限を制限する。
- [ ] Sparkle 秘密鍵、Developer ID の秘密鍵、公証資格情報を分けて管理し、権限・保管場所・バックアップ・復元担当を記録する。秘密鍵や認証情報を Git、ログ、配布物に含めない。復元手順は安全な試験環境で確認する。
- [ ] 公開鍵の切替えは既存版が新しい更新を検証できる移行経路を事前に設計し、旧版から実機試験する。鍵の紛失・漏えい時の更新停止、証明書等の失効、配信先の封鎖、利用者への周知と安全な再導入方法を準備する。署名鍵の漏えいでは署名済み更新を信頼できなくなるため、通常の更新だけで復旧できると仮定しない。
- [ ] 初回 pkg、更新 zip、署名済み feed と公開後に HTTPS から取得した成果物が対応することを確認する。過去の URL と履歴、版番号、署名、サイズも確認し、古い feed や CDN キャッシュによる配信を試験する。危険な版の配布停止と訂正版の提供手順を用意する。
- [ ] [Sparkle 実機検証](sparkle-physical-validation-ja.md) の全ケースを製品版の条件で実施する。正常更新だけでなく認証拒否、通信断、改ざん、取消し、中断、再起動、設定保持、所有権、サービス再接続と物理入力を確認する。失敗時に安全な更新方式が成立しなければ配布しない。

## 入力の安全性と復旧

- [ ] 別の入力手段と復旧可能な試験 Mac を確保し、キー押下中の停止・クラッシュ、スリープ／復帰、画面ロック解除、OS 再起動、デバイスの抜き差しと複数キーボードを試す。押しっぱなしや入力不能が残らないことを物理的に確認する。
- [ ] 入力監視・アクセシビリティの拒否や取消し、ドライバ未導入・停止・不一致、サービス承認待ち、複数ユーザーとユーザー切替、他の入力ツールとの競合を確認する。未対応や競合がある条件は明記する。
- [ ] 設定のバックアップと復元、設定破損・インポート失敗、旧版と新版の設定互換性を確認する。既知の旧版への復帰は実際に試し、互換性が確認できない場合に安易な上書き復元を案内しない。
- [ ] [利用者向け復旧・削除手順](install-update-ja.md#入力できなくなった場合) を別端末から閲覧できる正規の公開先に用意し、画面の操作名と実機での有効性を確認する。共有ドライバや他製品を無断で削除しない。

## 入力情報と権限の説明

- [ ] 公開する版のデータフローを確認し、取得する入力・デバイス情報、EventViewer の表示・保持、設定やログの保存場所、保持期間、外部送信の有無と送信先を利用者向けに記載する。Sparkle の更新確認では配信サーバーに通信が発生するため、運営者が取得できるアクセスログと保持期間も確認する。未確認の事項を「送信しない」「保存しない」と断定しない。
- [ ] 入力監視を Core に、EventViewer 使用時のアクセシビリティを Agent に求める理由、root サービスとバックグラウンド項目、共有ドライバの役割を説明する。アクセスを拒否した場合の動作と、OS 設定からの許可撤回方法を確認する。
- [ ] パスワード欄やセキュア入力中の EventViewer の抑止を実機で検証する。診断・問い合わせの際に入力履歴、設定、個人情報、秘密情報を不用意に送らないよう案内し、受領・保存・削除の方法を決める。
- [ ] 設定ファイルには `shell_command` が含まれ得ること、インポート内容を確認し信頼できない設定を読み込まないことを説明する。実行は Agent のユーザー権限で行われる。

## 権利・ドライバ・サポート

- [ ] [権利確認](publication-rights-ja.md) に従い、公開する全履歴・バイナリ、依存物の通知、素材、名称、公式ドライバ pkg の再配布範囲を確認する。秘密情報スキャンと内容確認は公開直前に実施し、検出時は公開を止め、必要に応じて認証情報を失効する。
- [ ] 対応する公式 VirtualHID の版、公式入手先、署名と公証、OS の承認、他製品との共有、削除時に残る項目を確認する。ReKey と pqrs.org 等との関係を誤認させない。独自拡張を出荷する場合の資格と条件は別途確認する。
- [ ] 脆弱性の非公開報告先と通常の問い合わせ先を決め、公開ページに記載する。報告時に必要な版・OS・再現手順、秘密情報を含めないこと、初回応答と修正・告知の運用方針を決める。未設定の窓口を実在するものとして記載しない。
- [ ] 各リリースの変更点、既知の不具合、対応・試験済み環境、更新方法とサポート範囲を掲載する。深刻な問題時の配布停止、調査、修正版・回避策の提供、告知と担当者の連絡経路を決める。

## 継続保守と配布の終了

- [ ] Sparkle、VirtualHID、その他の依存物と macOS の変更・脆弱性情報について、確認する公式情報源、担当者、確認頻度と記録先を決める。影響を受ける版を特定し、更新の必要性、互換性、ライセンス通知の変更と実機試験を確認する。上流の配布停止・非互換変更時の代替や利用者への案内も検討する。
- [ ] 開発を休止・終了するときの担当者と告知先を決め、最終対応版、サポート終了日、既知の問題、更新停止後のリスク、アンインストール・設定保存・復旧手順を案内する。更新確認に失敗した場合のアプリの挙動も実機で確認する。
- [ ] 更新 feed、配布物、復旧案内の URL と、それらに関わるドメイン・アカウントの管理者、更新期限、支払方法、引継ぎ手順を記録する。終了時も必要な期間は安全に管理し、失効や第三者への移転で偽の案内・更新先にならないよう対策する。管理を続けられない場合の告知・移行方法を事前に決め、更新署名の検証があることだけを理由に配信先の管理を省略しない。
- [ ] 引継ぎ時はアカウントと鍵へのアクセスを個別に移管・棚卸しし、不要な権限を削除する。秘密鍵を公開文書に記載せず、鍵の復旧・ローテーションと既存利用者への影響を確認する。

## 公開ページと障害時の案内

- [ ] 配布ページに開発版・安定版の区分、実際に試験した OS・機種・ドライバ、既知の不具合、サポート対象と対象外を示す。公証は Apple の自動検査であり、品質や安全性を保証するものとして説明しない。
- [ ] 復旧ページはスマートフォンなど別の端末から検索・閲覧できるよう、正規の配布ページとリリースノートからリンクする。入力できない状況を想定し、マウス等で行える操作を先に示す。コマンドが必要な場合は別の入力手段を前提として明示し、OS ごとの画面名と手順を実機で確認する。
- [ ] 配信先の障害、アカウント停止、通信制限や更新サーバーの問題を知らせる独立した告知先を決める。代替配布先を使う場合は正規性を利用者が確認できるよう事前に案内し、署名・公証と更新署名の検証を維持する。
- [ ] 脆弱性は公開 Issue に機密情報や悪用可能な詳細を書かずに報告できる連絡先と、受領・調査の担当を用意する。報告者との連絡、影響範囲の確認、修正前の情報共有範囲、修正後の影響版・更新方法・回避策の告知を決める。窓口や対応期限を決定するまでは約束済みと記載しない。

## 配布サービスと法令・契約

- [ ] 採用する配布先の現行規約、容量・転送量・料金、利用制限、アカウント維持条件を公開前と変更時に確認する。想定アクセスによる費用、制限到達時の動作と担当者への通知、障害時の告知方法を決める。実際の契約や利用量を確認するまで無料・無制限と断定しない。
- [ ] 問い合わせ、アクセスログ、診断情報などで実際に受け取る情報、利用目的、保存先・期間、削除方法、委託先と対象地域を整理する。運用実態に合うプライバシー案内を用意し、収集しないと断定する前にアプリと配信側を確認する。
- [ ] 寄付、販売、有料サポートや海外向け提供を行う場合は、その提供方法と対象地域に応じて、消費者保護、税務、個人情報その他の法令・契約条件を確認する。必要に応じて専門家に相談し、確認結果と適用範囲を記録する。これらの項目は特定の法的義務が生じると断定するものではない。
