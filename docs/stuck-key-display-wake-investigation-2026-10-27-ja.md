# 消灯直後の再点灯とキー押下残留の調査

調査日: 2026-10-27 20:02〜20:05 JST。対象ソース: `da006a7`。

## 結論

**実機で「常にどこかのキーが押されたまま」とは確認できなかった。押下が残っていないとも断定できない。** OS のキー状態取得は権限不足・タイムアウトで完了せず、消灯と再点灯の瞬間の入力も採取できていない。

一方、ReKey の変換エンジンでは、**押下を受け取った後に解放入力だけが届かないと、出力キーが押された状態で残り得る**。`international2 → Return` の人工入力で再現した。通常の長押しと区別する仕組みはなく、この実験だけで不具合や実機の発生原因とは断定できない。

無入力からキーを無条件に定期送信する処理は、調査した Core の通常経路には見つからなかった。キー状態の残留、入力イベントの継続発生、画面再点灯の因果関係は別々に確認する必要がある。

## ソースから分かったこと

- `Core/Engine.hpp:201–215`: 押下状態を記憶し、対応する解放入力で出力を解放する。重複した押下入力は無視する。通常の JIS → Return もこの経路。
- `Core/Engine.hpp:191–199`: `release_all()` は保持キーを解放する。一方、`tick()` は同時押し待ち・長押し判定・緊急停止を処理するが、通常キーの長時間保持だけを理由に解放しない。
- `Core/HIDReports.hpp:28–42`: 複数入力の出力キーを参照カウントで保持する。全入力の解放が揃うまで同じ出力キーを保持するため、片方の解放欠落でも残り得る。
- `Core/core.mm:41–49`: デバイス除去、設定再コンパイル、停止、キュー異常には解放・リセット処理がある。ただし、切断通知なしで解放イベントだけが欠落する場合の物理キー状態との照合はない。
- `Core/core.mm:98–111`: 5ms ごとの処理はあるが、無条件のキー出力ではない。「10秒出力なし」の監視は累積 `outputs == 0` の条件で、すでに押下を1件出力したケースの残留検出にはならない。
- `Core/VirtualHIDOutput.hpp:46–66`: 100ms 待機はキュー処理と監視用。通常はキューの入力に応じてレポートを送る。世代変更時には空レポートでリセットする。2秒の監視は入力ループ停止を検出するもので、ループが動いたまま解放入力だけが欠落するケースは検出しない。
- `Core/core.mm` には、画面消灯通知やシステム sleep/wake 通知を直接受けて押下状態を照合・解放する処理は見当たらない。実際に消灯時に解放が失われるかは未検証。

## オフライン再現と既存試験

調査用 `CoreValidation/stuck_key_probe.cpp` は OS 入力やデバイスを操作せず、エンジンだけを呼ぶ。現在設定のコピーではなく、JIS キー1件だけの合成設定を使用した。

```sh
xcrun clang++ -std=c++23 -O2 -ICore \
  -isystem Vendor/VirtualHID/vendor/vendor/include \
  CoreValidation/stuck_key_probe.cpp -o /tmp/rekey-stuck-key-probe
/tmp/rekey-stuck-key-probe
```

| 条件 | 結果 |
| --- | --- |
| 無入力で60秒相当の `tick()` | 出力0件 |
| `international2` の押下と解放 | Return の押下・解放が各1件 |
| 同じキーの押下を重複させてから解放 | 重複出力なし、Return を解放 |
| 押下のみ渡し、60秒相当の `tick()` | 最初の Return 押下のみ。自動解放も追加送信もなし |
| その後 `release_all()` | Return 解放1件。直前まで内部の押下が残っていたことを確認 |

実時間60秒のハードウェア試験ではなく、時刻引数を進める実験。Bluetooth の解放欠落、DriverKit、OS のキーリピート、再点灯を再現したものではない。

`scripts/test-core.sh` は49,657アサーション、共有キー参照カウント、4種類のHIDレポート、リセット、キュー、入力ループ停止監視を含めて成功。既存ランダム試験は最後に `release_all()` を実行するため、解放入力の欠落を自動検出・修復できる証拠にはならない。

## 原因確定に必要な確認

1. 再発時に実機の押下状態と、物理入力・仮想出力の押下／解放の対応を採取する。長時間押下の有無だけでなく、無操作中の反復入力も調べる。
2. 入力を離してから数秒後に消灯し、ReKey 有効／一時停止の条件で比較する。現象の不規則さがあるため1回の成功だけで原因を確定しない。
3. MX Ergo S の電源を切った条件でも比較する。活動記録に名前が出たことだけでは原因と決めない。

今回は調査と再現資料の追加のみ。消灯操作、ReKey の一時停止・再起動、設定変更、アプリの更新は実施していない。キー状態取得の診断プロセスは中断またはタイムアウトで終了した。

## 調査後の修正（2026-10-27）

上記は調査時点の記録。調査後、次の予防処理を追加した。

- `IORegisterForSystemPower` のシステム sleep/wake と、`IODisplayWrangler` の電源低下・復帰通知をメインループで受信する。スリープの可否確認と開始通知には `IOAllowPowerChange` で応答し、スリープを拒否しない。
- 状態変化時に全デバイスの変換状態、保留アクション、Viewer 記録を破棄し、入力デバイスを解放する。出力世代も更新し、旧世代のキューを無効化して4種類の空HIDレポートを要求する。出力ワーカーの送信は非同期で、スリープ直前にOSが受け取ったことまで保証するものではない。復帰時にもリセットする。
- 消灯側またはシステム側が休止中なら、5msタイマーによる入力デバイスの再取得と入力処理を止める。両方の復帰後に通常の取得を再開する。物理キーボードは解放されるため、復帰操作はOSに届く。
- 再取得より古い時刻のHID値を除外する。`release_all()` で緊急停止の長押しタイマーも消し、復帰後に過去の操作が緊急停止を発火させることを防ぐ。
- 調査用 `stuck_key_probe.cpp` をSwiftのライブラリ対象から除外した。独立した `main()` がアプリ・Agentにリンクされ、重複シンボルでビルドが失敗していたため。

通常の長押しを一定時間で強制解除する処理は追加していない。消灯やスリープを伴わずに解放入力だけが欠けた場合の物理状態照合も未実装であり、その場合は既存の停止・切断などによる解除が必要。

- `scripts/test-core.sh`: 49,701アサーション成功。解放欠落のJIS→Return、60秒相当の長押し、display/system通知の順序違いと重複、片方だけ復帰した状態、遅延した解放入力、復帰後の新しい押下・解放、緊急停止タイマーの取消を含む。既存の4種類のHIDレポート、共有キー、キュー、ワーカー監視試験も成功。
- `swift test`: 28テスト成功。
- `scripts/build-app.sh`: Core、Swiftリリースビルド、アプリへの格納・アドホック署名が成功。候補アプリは `build/ReKey.app`。
- 実機で消灯・sleep通知の登録のみを行う一時診断: `system registration=1 display registration=1`。通知の実到着やリセットのOS反映を確認する試験ではない。

インストール済みアプリの更新、実際の消灯・スリープ操作、再点灯現象の再現試験は実施していない。原因確定に必要な実機比較は引き続き上記の手順を使う。通知登録が失敗した場合はシステムログに記録するが、その経路の解放処理は利用できない。
