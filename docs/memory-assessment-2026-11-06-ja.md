# ReKey のメモリ消費とリファクタリング案

調査日: 2026-11-06（JST）。ソースの基準: `4260cfc5277ebef283444f951d182efbacaff009`。
実機対象: `/Applications/ReKey.app`、0.1.0 / build 17、PID 1673。

## 結論

**削減を狙うリファクタリングは十分に可能。最優先は GUI の変更通知の蓄積を止めること。**

画像の約700 MBは実機でも再現した。ヒープの大きな部分を Swift Observation の追跡・登録用オブジェクトが占めている。入力エンジンのアルゴリズムや仮想 HID を作り直すより、GUI の状態管理と定期更新を整理する方が有望である。

ただし、今回特定できたのは「どこにメモリがあるか」まで。どの画面・プロパティ・フレームワーク経路が保持し続けているかは未確定で、削減量の保証はできない。アプリ本体の変更、再起動、サービスの停止、設定変更は行っていない。

## 実測

`ps`、`vmmap -summary`、`heap -sortBySize` で測定した。画像と同じ PID 1673 は、10月30日09:33から約7日間起動していた。

型名に Observation が明示された上記4種類だけでも約364.8 MiB。関連が疑われる AnyKeyPath の Set を加えると約506.0 MiBで、全 malloc 割当の約73%。Closure context は所有元が分からないので、Observation の合計には含めない。

## 優先順位と変更案

| 優先度 | 変更案 | 期待する効果 | リスク・限界 |
| --- | --- | --- | --- |
| 1 | UI公開状態と通信・タイマー内部状態を分離する | Observation の追跡対象を減らし、大きな保持領域の原因を切り分ける | 単に属性を付けるだけで既存の蓄積が解消する保証はない |
| 1 | 値が変わったときだけ UI 状態を更新する | 3秒ごとの不要な変更通知・再評価を減らす | 値の比較項目を漏らすと表示が更新されない |
| 2 | 設定画面と EventViewer の状態・寿命を分ける | 閉じた画面の監視や表示データを解放しやすくする | 保存、一時停止、終了時動作を維持する必要がある |
| 3 | KeyPicker のメニュー構築と一覧を軽量化する | 設定行が多い場合のビューとクロージャの数を減らす | 今回の蓄積源かどうかは未確認 |
| 4 | EventViewer のバッチ更新・リングバッファ化 | 頻繁な配列更新と先頭削除のコストを抑える | 2,000行の上限は既にある。700 MBの主因という証拠はない |
| 5 | Agent の設定キャッシュ・イベント通知化 | JSON再解析と周期処理の割当を削減する | 今回Agentは測定できておらず、GUI問題とは別に検証する |

### 1. 状態管理と通知を最初に整理する

根拠: `Sources/ReKeyApp/AppState.swift:31–80,271–295`、`Sources/ReKeyApp/RuntimeClient.swift:33–75`。

- `AppState` と `RuntimeClient` はどちらも `@Observable`。Task、XPC接続、通信中フラグ、前回ファイルデータ、HID Managerなどにも `@ObservationIgnored` の指定がない。UIが直接読む必要のないものを非観測のサービスに移すか、観測対象から除く。`private` だけでは非観測化の指定にはならない。
- `AppState` は3秒ごとに `refreshSystem()` を実行し、同じ値でも前面アプリ、ドライバ状態、デバイス一覧などを代入する。`RuntimeClient` も応答のたびに `status` を代入する。`RuntimeStatus` を比較可能にし、デバイス一覧や表示用状態も差があるときだけ公開する。
- メニューバーが必要とする少数の値をまとめ、設定全体への依存を狭める。通信中フラグの変化まで画面の更新に伝わらない構成にする。
- 観測の蓄積が続く場合は、該当する状態だけ明示的な通知方式への置き換えを比較する。SwiftUI全体を作り直す判断は、その結果を見てから行う。

この変更を小さく分けて測定すれば、アプリ側の更新方法で回避できるのか、OS / SwiftUI / Observation 側の保持が関わるのかを絞れる。現時点ではどちらの不具合とも断定しない。

### 2. 常駐部分と画面の寿命を分ける

根拠: `Sources/ReKeyApp/ReKeyApp.swift:5–35`、`Sources/ReKeyApp/SystemViews.swift:145–183`。

アプリ全体の `@State AppState` を設定・メニューバー・EventViewerで共有している。常駐用の小さな状態と、設定編集用・イベント表示用の状態を分け、画面を閉じたときに画面用の監視を止める。

ただし、**Coreの状態確認を単純に止めてはいけない**。`Core/core.mm` は `status` 呼び出しでUIの生存期限を5秒延長し、`disable_on_quit=true` で期限が切れるとリマップを停止する。現状の3秒ポーリングを間引くなら、生存確認と画面データ取得を分離する設計が必要になる。表示を閉じただけでリマップが止まる変更を避ける。

### 3. 大きな画面だけ必要に応じて軽量化する

根拠: `Sources/ReKeyApp/SettingsView.swift:100–129,196–209`、`Sources/ReKeyModel/KeyCatalog.swift`。

各KeyPickerは11カテゴリのサブメニューとキー候補を持ち、単純リマップの各行に2個置かれる。行全体も `ScrollView + VStack` で構築される。候補の共通化、選択中だけ候補を生成する方式、必要に応じた `LazyVStack` や AppKit メニューを比較する。実際のメニュー実体化タイミングはフレームワーク依存なので、行数を変えた測定で判断する。

`KeyCatalog.label()` 内の辞書やカテゴリ配列の共有化も候補だが、コンパイラの最適化もあるため、単独で大きな削減を見込むものではない。

### 4. EventViewer と Agent は次段階

`RuntimeClient` の表示履歴は既に最大2,000件で、Coreも2,048件の固定配列を使う。無制限のイベント履歴という構成ではない。空のバッチでの更新回避、まとめて表示、上限付きバッファへの変更はできるが、優先度は低い。

Agent は100 ms周期で動き、約1秒ごと、または前面アプリ変更時に `store.load()` から設定の読込・検証を行う。設定変更時だけキャッシュを更新する余地がある。AXによる入力欄確認とコンテキストの鮮度500 ms、Viewerのリースを維持する必要があるため、一律に周期を長くする案は採らない。

## 効果の見込みと検証方法

**数百 MiB規模の保持領域を改善対象にできるが、それがそのまま削減量になるわけではない。** 約506 MiBには必要な追跡状態も含まれる。起動直後の基準値、解放可能量、安定後の到達値は未測定で、「700→50 MB」などの到達値は約束できない。

実装は次の順に進めると、効果と原因を評価しやすい。

1. 同じ署名・releaseビルド・設定・OSで変更前後を比較する。設定画面を閉じた状態、開いた状態、メニュー開閉、EventViewer使用を分ける。
2. 非観測化と同値更新の抑制を別々の変更として試す。各条件で起動後のウォームアップを取り、30〜60分、続けて24時間以上の footprint と追跡オブジェクト数を見る。
3. まず「放置で追跡オブジェクトが増え続けない」を合格条件にする。画面・メニューの反復開閉後、増加が収束するかも確認する。
4. 改善しなければ、診断専用ビルドを Allocations / Memory Graph / MallocStackLogging で調べ、巨大なObservation Dictionaryの所有元と割当経路を特定する。ヒープ型名だけでは保持経路を確定できない。
5. 既存の Swift / Core テストに加え、リマップ継続、5秒の生存期限、設定の競合保存、プロファイル切替、EventViewerのパスワード欄抑止を実機で確認する。

今回の成果物は調査文書と測定抜粋のみ。コード変更を伴わないため、ビルド・機能テストは実行していない。
